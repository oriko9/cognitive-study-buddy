> This is not a test the suite runs. It is the reasoning trail for Turn 2's
> planned observation (`specs/spiral-log.md`): whether `models/gemini-3.1-flash-lite`
> grades a free-text answer on meaning, or merely on the presence of the right
> formula. The question is real, generated by the live deploy against a real
> Hebrew probability deck (Turn 1's real-deck run). The five answers are
> written by hand to probe grading, each labelled and given an expected score
> band **before** any of them is run against the live model — so the result
> cannot be fitted to the label after the fact.
>
> **Decision rule (set in `specs/spiral-log.md` Turn 2, before this file
> existed):** if a wrong answer scores above 0.5 more than once across this
> set, route the evaluation call to a stronger model and cut the per-user cap
> to match its quota.

## The question

Generated by the live deploy from a real Hebrew probability deck

- **Topic:** התפלגות גיאומטרית ותכונת חוסר הזיכרון (page 5)
- **Question:** הסבר במילים שלך מהי תכונת 'חוסר הזיכרון' של ההתפלגות הגיאומטרית,
  וכיצד היא משפיעה על חישוב הסתברויות מותנות עבור משתנה מקרי בעל התפלגות זו?

## Why answer 3 is the key case

Answer 3 deliberately **reuses the correct answer's own formula**,
`P(X > k+n | X > k) = P(X > n)`, and states it explicitly — but attaches the
opposite, false conclusion to it: that the conditional probability *decreases*
as the number of past failures grows, as though the variable "remembers" and
compensates for them. A grader that pattern-matches the presence of the
correct formula, rather than checking what the answer actually claims about
it, would score this high. A grader that reads for meaning would not. This is
the case the happy-path tests in `api/_lib/call-model.test.ts` and
`src/lib/schema.ts`'s tests cannot reach — a stub returns the score it is
given, so a confidently-wrong answer scored as correct is invisible to every
offline test in this suite (`specs/specification.md` §5, item 9).

## How this gets filled in

Each answer is run by hand through the deployed cycle against the question
above. The observed score and justification are recorded back into this file
(the "Observed score" column, plus the justification text if it disagrees with
the expected band) before `specs/spiral-log.md` Turn 2 records the Observed /
Changed-as-a-result entry. No score in this file is filled in by anything
other than a real call recorded as it happens — filling a band from
expectation rather than from a run would be exactly the rationalisation this
fixture exists to prevent.
